## 1. Summary

We built three concrete resource kinds on scout-ai's agent-level virtual
Path interface (`lib/scout/llm/agent/path.rb`): `task`, `entity`,
`entity_property`, each covering the full resource lifecycle — draft
creation in a `tmp` location, validation, real on-disk tests executed in
fresh subprocesses (including an end-to-end smoke run), and promotion into
the TestWF project tree — plus the complete generic operation set
(read/write/edit/list/move/rename/delete) with sandbox-verified traversal
rejection. All generic operations work for all three kinds (step 4
round-trips, 8/8 checks each), the special operations work end-to-end
including a genuinely failing test being reported as failing (step 3 +
step 4), and six friction hypotheses about `path.rb` itself were
behaviorally confirmed, two of them refined from their step-1 source-only
form. The investigation also established the minimal no-model wiring
recipe (`LLM::Agent.new` + `load_path_plugins`) and the fact that the
class-level registry is unreachable without the model-dependent `path`
chat role. What remains is a set of `path.rb` defects/gaps (section 4)
and a decision about where the kinds should live long-term (section 6).

  no `smoke` operation exists in the vocabulary, and inventing one would
  make `path_kind_capable?` return false and hide the tool (step 2 notes).

  `share/test/entity_property/<entity>/<entity>.<property>.rb`.

- **Plugin format**: declarative definitions plus `validate`/`test`/
  `promote` lambdas; shared runner logic lives in

## 4. Confirmed gaps and defects

Behavioral verdicts from `tmp/probes/step4/out/hypotheses.txt` (one probe
script, one run; the exception classes cited below were captured verbatim
in that run — UNVERIFIED in the sense of not independently re-run, though
each case is deterministic and the classes match the source paths cited):

- **H-A — `path_list` location handling is two-layered.** A location not
  in `locations` → clean `ParameterException` ("Location ... is not
  supported"). A location *declared* but missing from `roots` → raw
  `KeyError: key not found: "project"` from `roots.fetch` (path.rb:551).
  *Correction over step 1*: step 1 described only the KeyError branch;
  the undeclared branch is well-behaved. Impact: a kind with an
  inconsistent declaration turns every `path_list` call for that location
  into an uncaught exception; contrast `resolve_path` (path.rb:350),
  which silently falls back to `Scout.root.find(:current)` for `project`
  — inconsistent handling of the same condition.
- **H-B — `path_authorize!` absolute-path preconditions.** (i) relative
  root string → `ParameterException: Path sandbox requires absolute
  filesystem paths`; (ii) `resolve` lambda returning a relative string →
  same exception. (iii) *CORRECTED*: a `resolve` lambda returning a
  `Scout::Path` object **works** when the underlying path is absolute —
  `path_authorize!` calls `target.to_s` and accepts any object whose
  string form is absolute (path.rb:390–394). Step 1 predicted a
  ParameterException for non-String returns; that holds only for relative
  returns. Impact: kinds must keep roots absolute; resolvers returning
  Path objects are safe as long as their string form is absolute.
- **H-C — promote destination authorization is the lambda's job.** The
  framework `path_promote` authorizes only the source with `:write`; a
  promote lambda that moved a file to a destination **outside both
  configured roots** succeeded at the framework level (probe then
  restored the file). Impact: any kind whose promote lambda forgets to
  re-authorize its destination has no framework safety net; this is a
  design contract, not an enforcement.
- **H-D — two-registry split.** Class-level
  `LLM::Agent.register_path_kind`/`PATH_KINDS` (Symbol keys) and the
  instance registry are disjoint by default: a bare `LLM::Agent.new`
  raises `ParameterException: Unknown path kind` for a class-registered
  kind. The only import path is `Agent#ask`'s handling of a chat message
  with role `path` (agent.rb:130–139, source-read; not model-executed).
  Impact: class-level registration is unreachable from non-LLM callers;
  workflows that rely on it silently lose their kinds in bare processes.
- **H-E — edit line-selector newline semantics.** `lines[start...end] =
  [replacement]` glues the replacement to the following line
  (`l1\nl2\nl3\nl4\n` + lines[1...3]="X" → `l1\nXl4\n`) and drops the
  trailing newline when the range reaches the last line (`l1\nXl4\nY`).
  The `version` input only reaches `doc_id`. Impact: callers cannot do a
  clean line replacement without manually embedding `\n`; data loss of
  the final newline is silent.
- **H-F — wrapper rescue scope.** The tool wrapper
  (`path_install_tool`, path.rb:175–190) rescues only `ScoutException`,
  converting it into the JSON error envelope. The H-A/H-F `KeyError`
  **escapes the wrapper raw** — the same inconsistent-kind declaration
  produces a hard exception on the tool surface, not an envelope.
  *Correction over step 1*: step 1 framed this as "direct calls raise
  raw"; in fact the wrapper does not contain KeyErrors either. Direct
  `path_*` calls always raise raw (`ParameterException` is a
  ScoutException subclass, so it does envelope correctly through the
  wrapper).
- **Non-addressable generated tests (step 3).** `share/test/...` sits
  outside both declared roots of any kind, so generated tests cannot be
  read/edited/listed through the kind interface. Evidence:
  `tmp/notes/ground-truth.md` step-3 section (path.rb friction).
- **No `parameters` schema extension (step 1).** The special-operation
  dispatcher passes only `(kind, path, location)`; arguments such as a
  custom test command or destination override are not expressible.
  Source-read (path.rb:690–712; `tools/definition.rb` has no per-kind
  parameter extension); exercised implicitly by every step-3 lambda
  needing no extra args. UNVERIFIED as a *negative* claim beyond one
  source pass.
- **New step-4 findings** (single probe run each):
  `path_list` with a nonexistent prefix authorizes against the nearest
  existing ancestor and returns `[]` silently; tool entries are
  `[callable, definition]` pairs, so probing requires
  `.first.call(name, args)`.

## 5. Not applicable / deliberately out of scope

Semantic execution stays outside the path layer: running a task, invoking
property dispatch, or resolving entity identifiers is Scout semantics,
not path-addressing semantics. The kinds deliberately encode only the
resource lifecycle (write/validate/test/promote); the `test` lambdas
perform semantic execution *as part of testing* (the task test runs a
clean Scout job, the property test calls the property on a synthetic
entity) because that is the only way a test can be meaningful — but the
path operations themselves remain generic. A semantic-operation layer
(e.g. `run`, `dispatch`) would belong above the path interface, not
inside kind definitions.

Also out of scope: making generated tests first-class kind resources
(they are plain files addressed by absolute path in the verdict; adding a
third location would force a third root into every `path_list`/resolve —
see H-A for why that is currently fragile), and productionizing the kinds
themselves (section 6).

## 6. Recommended next steps

Ordered; each is tied to the gap it addresses.

1. **Fix H-A + H-F together (highest impact, smallest change).** Make
   `path_list`'s root lookup consistent with `resolve_path`'s location
   check — raise `ParameterException` (not raw `KeyError`) when a
   declared location lacks a root, or fall back to the documented
   default; and widen the wrapper rescue to cover `KeyError`/`StandardError`
   so the tool surface always returns the envelope. This makes
   inconsistent kind declarations recoverable rather than fatal.
2. **Fix H-E in `path_apply_selector`.** Append the replacement's missing
   newline when the selector type is `lines` (i.e. join with `\n`
   semantics instead of array splicing), preserving the trailing newline
   when the range touches the last line. Cheap, self-contained, and
   removes a silent data-loss mode for every kind.
3. **Add promote destination authorization / a promotion-plan API for
   H-C.** Either authorize the destination inside `path_promote` (the
   framework knows the destination root when the lambda declares one), or
   provide a plan API (`promote_plan` returning source/destination/
   checks) so lambdas stop hand-rolling authorization. The current
   contract (lambda must re-authorize) is documented but unenforced.
4. **Decide the kinds' permanent home.** They currently live under
   `tmp/path_kinds/` as probe artifacts. Graduating them to
   `share/path_kinds/` (or a workflow task that registers them) would
   make `load_path_plugins` the documented loading story; the class-level
   registry (H-D) is not a viable alternative for non-LLM callers.
5. **Wire the `path` chat role for LLM callers (H-D).** If agents are
   meant to receive kinds, either import `PATH_KINDS` at agent
   construction or document the chat-role trigger; today the class
   registry is dead code for bare processes.
6. **Consider per-operation parameters** if any future special operation
   needs arguments (the missing `parameters` extension): today the
   signature is fixed at `(kind, path, location)`.

### H-B — explicit absolute-roots contract

Contract (plugin authors):

Every root a kind declares must be an ABSOLUTE filesystem path string (or
a Callable returning one; Scout Path-like objects are accepted and
stringified). Relative or non-path values are rejected at REGISTRATION
with a semantic error naming the kind, the location, and the offending
value, with the remedy "path kind roots must be absolute; use
File.expand_path". Roots supplied as Callables cannot be checked at
registration; their VALUE is checked at RESOLUTION time with the same
error. On the resolve side, a kind's `resolve` lambda may return either a
relative path (joined under the location root) or an absolute path — but
an absolute result must be unambiguously CONTAINED under the root
(lexically normalized: equal to the root or beneath `root + "/"`;
`..`-escapes and absolute-elsewhere results raise the same semantic error
family). Symlink escapes at operation time are still denied by
`LLM::Sandbox.authorize_path`'s realpath pass; H-B's containment check is
lexical and shares the `path_contained?` helper with the move gate rather
than duplicating enforcement.

- Methods: `register_path_kind` (registration-time check + inline
  contract comment), `path_project_root` (callable-root value check),
  `resolve_path` (resolve-output containment), `path_contained?` (new
  shared helper).
- Tests: relative root rejected (kind+location+value in message),
  non-string root rejected, callable root relative value rejected at
  resolution, resolve `..`-escape rejected, resolve absolute-outside
  rejected, legitimate forms still pass (absolute root, in-root resolve,
  plain relative resolve joining root).
- Compatibility: the checkout's three kind drafts + runner register and

## R2.4 Known boundaries

What the engine does NOT defend:

- **Trusted-plugin lambdas performing raw filesystem calls in-process.**
  Kind lambdas are trusted Ruby code running inside the agent process;
  the engine authorizes the paths it hands them and the destinations they
  declare, but it cannot intercept arbitrary `FileUtils`/`File`/`IO` calls
  the lambda makes on its own (`rogue_promote` proves this). The real
  boundary for that class of risk is the bwrap sandbox around the agent
  process.
- **Rerun caveats.** The round-1 probe suite was written for a one-shot
  clean scaffold; reruns inherit filesystem state (pre-promoted drafts)
  and the suite reports it (`round2-regression.md` D3). Reproduction
  commands in section 8 assume a fresh scaffold or idempotent re-runs.
